# Languages and translations (i18n)

Duopilo shows its dashboard, tool messages and tray texts in the language you choose; **logs are always English**. **English is the default** and the fallback; German is the first translation. This guide is for translators and developers.

## Choosing the language

- Dashboard: **Settings → Language** (applies immediately and is saved to `appsettings.Local.json`).
- Or in `appsettings.Local.json` next to `Duopilo.exe`:
  ```json
  { "Duopilo": { "Language": "de" } }
  ```
- Or the environment variable `Duopilo__Language` (e.g. `setx Duopilo__Language de`). Environment variables take precedence over the file.

Unknown codes fall back to English. Regional codes are shortened (`de-DE` → `de`).

## Language files

- One file per language: `src/Duopilo/i18n/<code>.json` (`en.json`, `de.json`, …), embedded in `Duopilo.dll` at build time.
- A flat JSON object of `"key": "text"`. Keys are dotted, with a camelCase last segment (`tools.traffic.noneAirborne`).
- Keys starting with `_` are comments for translators and are ignored (e.g. `"_comment": "…"`).
- `"language.name"` is the language's own name (`"English"`, `"Deutsch"`); the dashboard language selector shows it.
- **English is complete and is the fallback per key:** if a translation is missing a key, Duopilo uses the English text; if English is missing it too, the key itself is shown.

### Placeholders

- Named placeholders: `{name}`, or `{name:format}` with a .NET format string, always applied with the invariant culture (`{seconds:0.0}` → `2.5`, `{progress:P0}` → `40 %`).
- Literal braces: `{{` and `}}`.
- A translation must use the **same set of placeholders** as the English text. For ordinary keys it **may reorder** them, because Duopilo matches arguments by name.
- **`log.` keys are English only.** They are log texts (ILogger templates, crash reports) and exist only in `en.json`; translation files must not contain them, and Duopilo ignores them if they do. Logs stay English whatever the setting, so they can be attached to issues and read by every contributor.

### Tests

`tests/Duopilo.Tests/LocalizationTests.cs` enforces:

- English texts are not empty; every translated key also exists in English; German is complete (except `log.` keys).
- Same placeholders as English; no `log.` keys in translation files; `Loc.Log` returns English even with another language selected, and the log file stays English when an argument is a translated text.
- Every key used in the code (`Loc.T`, `Loc.En`, `Loc.Log`) and in `dashboard.html` exists in `en.json`.
- The number of arguments in a `Loc.T`/`Loc.En` call equals the number of distinct placeholders in the English text, and for `Loc.Log` the ILogger call passes one argument per placeholder occurrence.
- `Loc.Log` is only used with `log.` keys, and `log.` keys are never used with `Loc.T` (only `Loc.Log` or `Loc.En`).

## Key prefixes

| Prefix | Area |
|---|---|
| `tools.` | MCP tool results (message, note, hint, reason, error fields) |
| `input.` | Input module: prepare/confirm, interlocks, verification |
| `voice.` | Voice loop (microphone, recognition, dialogs) |
| `speech.` | Speech output settings and status (not the spoken text) |
| `atc.` | Duopilo ATC: service and status messages (not the radio texts) |
| `monitor.` | Pilot monitoring: alert explanations next to the English callout |
| `ecam.` | ECAM catalogue and status |
| `sim.` | SimConnect connection and facilities |
| `traffic.` | Traffic query and proximity |
| `aircraft.` | Aircraft profiles: loading, matching, warnings |
| `profile.` | Texts referenced from profiles, e.g. `profile.requires.<name>` for refusal texts of action conditions |
| `flightplan.` | SimBrief / OFP |
| `host.` | Startup, configuration, crash handling |
| `remote.` | OAuth, consent page, remote access |
| `settings.` | Dashboard settings API |
| `report.` | Bug reports ("report a problem") |
| `tray.` | Tray icon menu and balloon tips |
| `dashdata.` | Texts in the dashboard data API (`DashboardData.cs`) |
| `dashboard.` | Texts in `dashboard.html` (only these keys are sent to the browser) |
| `log.<area>.` | Log texts, English only: ILogger templates (e.g. `log.sim.reconnectFailed`) and crash reports |

## What stays English (crew-language policy)

Like a real crew working to SOPs, Duopilo keeps everything that is spoken or is phraseology in English, whatever the language setting:

- Callouts ("Positive climb", "Speedbrake retracted", "Gear not down"), including the `Callout` of an alert, and readbacks of actions ("Speed 250 set").
- Checklist items and responses, FMA mode calls, spoken warnings, TCAS/GPWS words.
- Radio and ATC: everything from `atc-templates.json` and every transmission or readback built for the radio.
- Everything passed to text-to-speech – the voices are English only.
- Speech **recognition** patterns (word lists and regexes such as `fahrwerk|gear`). They describe what the pilot may say, not UI text, so they may contain several languages.

What follows the setting: dashboard texts, tool messages (the explanation next to an English callout, reasons, errors, hints), settings and tray texts.

Logs are always English (for issues and international contributors): `duopilo.log`, crash reports and the log view in the dashboard.

Values in aircraft profiles and ATC templates are language-neutral: IDs, variable names, units, ICAO codes. Speeds are always in knots. A profile's refusal texts for action conditions are referenced by key (`"messageKey": "profile.requires.<name>"`); a literal `"message"` still works for self-made profiles and is shown as is. `description` and `notes` in profiles are technical metadata in English. See [aircraft.md](aircraft.md#texts-in-profiles).

## For developers

Namespace `Duopilo.Localization`.

- **`Loc.T(key, args…)`** – text in the selected language. Pass the arguments in the order the placeholders **first appear in the English text**:
  ```csharp
  // en.json: "tools.traffic.none": "No traffic within {radius} NM."
  return Loc.T("tools.traffic.none", radius);
  ```
  Write the English text so its placeholder order matches the call; translations can then reorder freely. Build each sentence as one key – don't glue fragments of different languages together.
- **`Loc.Log("log.…")`** – the message template for ILogger, always English. Keep the structured placeholder names (`{Message}`, `{Device}` …):
  ```csharp
  _log.LogWarning(ex, Loc.Log("log.sim.reconnectFailed"), ex.Message);
  ```
  Arguments are often texts the user sees translated (an alert message, a refusal reason, an error). `Loc.T` remembers the English
  twin of every translated text, and the file logger swaps such an argument (and an exception message) for its twin, so the line
  stays English. For a text you build from several parts just for the log, use `Loc.En(…)` or `Loc.ToEnglish(text)` on each part.
- **`Loc.En(key, args…)`** – always English: texts that only go into logs or crash reports, and `log.` keys outside ILogger.
- **`Loc.ToEnglish(text)`** – the English twin of a text `Loc.T` produced in another language (anything else unchanged).
- **Tests:** `using var _ = Loc.Use("de");` sets the language for the current async flow only and restores it on dispose. Tests run in parallel, so **never call `Loc.SetLanguage` in tests**.
- `const` fields and attribute arguments can't call `Loc.T`: keep the key as the constant and translate at the use site.
- Spoken text, phraseology and recognition patterns never go through `Loc.T` (see the policy above).

### Dashboard (`dashboard.html`)

The page receives the `dashboard.` keys of the selected language embedded in the HTML (`GET /api/i18n?lang=<code>` returns them for switching without reloading). Mark up texts with attributes:

| Attribute | Sets |
|---|---|
| `data-i18n="dashboard.…"` | text content |
| `data-i18n-html="dashboard.…"` | inner HTML (for texts with markup) |
| `data-i18n-title="dashboard.…"` | `title` |
| `data-i18n-placeholder="dashboard.…"` | `placeholder` |
| `data-i18n-aria-label="dashboard.…"` | `aria-label` |

In the script, use `t("dashboard.…", { name: value })`; parameters are passed by name. All keys used in the page must exist in `en.json` (checked by `DashboardKeysExist`).

## Adding a language

1. Copy `src/Duopilo/i18n/en.json` to `src/Duopilo/i18n/<code>.json` (two-letter ISO 639-1 code, lowercase, e.g. `fr.json`).
2. Set `"language.name"` to the language's own name (`"Français"`).
3. Translate the texts. Keep keys and placeholders, and remove the `log.` keys (logs stay English). Leave out keys you don't translate – they fall back to English.
4. Build. The file is embedded automatically and appears in the dashboard language selector. Run the tests to check placeholders.

**Try a translation without building:** put `<code>.json` into `%LOCALAPPDATA%\Duopilo\i18n\` (the `i18n` folder inside the data folder; respects `Duopilo:DataDirectory`) and restart Duopilo. Its keys override the embedded ones key by key, so a partial file is fine, and a new code adds a new language. A broken file is skipped.
